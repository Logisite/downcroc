# 1.3.6.post2

Adds privilege tiers and password-based approval to the extension system, plus
a full authoring guide so nobody has to read daemon source to write an
extension. Also fixes daily stats limits and review-menu ordering.

## Extension privilege layers

Extensions now have three layers.

**Layer 0** is the daemon itself. Vault files, SQLite, service objects, and
signal handling stay here. No extension ever gets direct access.

**Layer 1, standard**, is the default. It runs as a child process, speaks JSON
lines, and can use only standard capabilities such as `message.get`,
`mail.reply`, `kv.*`, `log`, and reporting calls.

**Layer 2, elevated**, is for extensions that need deep access. It still runs
as a subprocess by default, but after approval it may call capabilities such as
`http.request`, `cli.run`, `config.set`, policy and service control, vault
operations, transport changes, backup and restore, and database maintenance.

Capability tier is checked before grant in the broker. A standard manifest that
requests an elevated capability is refused at load time.

## Approval and password behavior

```sh
downcroc extension approve ID
```

The command prompts for the vault password even when the vault is already
unlocked. If the vault is locked, the same password unlocks it and approves the
extension in one step. Approval is per extension. There is no global session
that skips the prompt for the next one.

Approval stores an extension id, manifest digest, capability digest, tier, and
time. It stores no password and no derived key. Changing the capability list,
tier, or artifact checksum revokes approval automatically. Reload and approve
again after a change.

```sh
downcroc extension revoke ID
downcroc extension approval ID --json
```

If the vault locks after approval, the approval remains. Capability calls that
need secrets fail with `vault_locked` until you unlock again. Calls that do not
need secrets keep working.

New audit events: `extension.approved` and `extension.revoked`. They contain the
extension id and tier or reason, never a secret.

## Capabilities that changed

`cli.run` is now real. It runs `python -m downcroc <argv>` in a subprocess with
a timeout, no shell, and daemon-token redaction on both output streams. It
returns `returncode`, `stdout`, and `stderr`.

`capability.list` returns every registered capability with its tier.

All existing capabilities were classified as standard or elevated. No new raw
credential, arbitrary shell, filesystem, SQLite, or in-process import capability
was added. Those remain Layer 0 only.

## Documentation

The extension docs are now an authoring guide, not a command list. Under
`part-ii/28-extension` there are chapters for:

- writing an extension from an empty directory
- the exact wire protocol: `hello`, `event`, `actions`, `result`, and `error`
- every capability with parameters, results, and examples
- elevated extensions, approval, and vault lock behavior
- artifact build, verification, and replacement
- troubleshooting

The guide includes complete copyable `__main__.py` programs, including a reply
bot that deduplicates with KV and calls `mail.reply`. The acceptance rule for
this release was that no one should need to read source to write an extension.

## Other fixes

- Daily stats rows keep the quota limit that was stored for that day. A rebuild
  no longer rewrites past days with today's policy.
- The approve/review menu now honors `[cli] list_order`, so it follows the same
  ordering as the other listings.
- `VaultService.verify()` checks a password without changing vault state, so
  approval works while the vault is unlocked.

## Compatibility

Existing manifests and installed `.pyz` artifacts keep working. Manifests that
request elevated capabilities must be changed to `tier = "elevated"` and
approved. Nothing about the JSON protocol changed for standard extensions.

## Acceptance

Black-box tests cover approval denial before approval, approval with the vault
password, revoke, real `cli.run` output with token redaction, reply sending,
artifact build and verification, corruption detection, review ordering, and
config schema completeness.

Migration `96073f83071c` adds `extension_approvals`. The daemon runs it at
startup. ruff, format, docs map, glossary, lock, and compileall all pass.
