# 1.3.5.post5

Reworks SMTP seat ownership so one account holds the seat only while it can
actually use it, and releases it on real reasons such as quota exhaustion,
failure, or finished work.

## What changed

Earlier post releases tried to make the seat sticky by never releasing it, then
by letting other accounts borrow it. Both were wrong. This release models the
seat as an assignment to the account that can use it right now.

A new owner is chosen only when there is no owner or the owner is released.
Candidates are accounts with work in the current cycle, a usable SMTP binding,
and allowance left. Selection is weighted by the live transport list: an
account with one enabled and healthy transport is favoured over one with two,
and so on. Disabled, unhealthy, or cooling-down bindings are excluded. Provider
type and password versus OAuth are no longer used as a shortcut.

The owner keeps the seat while it has work and can send. It is relieved when:

- its sending allowance is exhausted
- its SMTP binding becomes disabled, unhealthy, or cooling down
- a send or transport fails
- its work is finished, now the default via `smtp_seat_after_batch = true`
- an optional `max_s` or `max_sends` cap fires

Read-only commands still never change the owner. `dispatch.smtp_seat` records
the real hold duration, real send count, previous owner, reason, and source.
`dispatch.slot_assigned` and `dispatch.slot_released` use the same reason. The
dispatcher also prefers the owner when picking the next job, so the seat is
actually used while it has work.

## What you should see

With one SMTP seat, `dispatch.slot_plan` stays on one active account while that
account has work and allowance. Other accounts continue through their API
bindings. When the owner's allowance runs out, its work finishes, or its SMTP
path fails, the seat moves to another eligible account and the old owner returns
to the fleet. No configuration change is required, but you can set
`dispatch.smtp_seat_after_batch = false` to keep the owner across gaps in work.
