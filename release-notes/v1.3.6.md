# 1.3.6

Adds an extension system so other people and agents can add behavior to downcroc
without changing daemon source. Extensions can react to events and ask the daemon
to perform credentialed work, with a reply-to-repliers bot as the first real
example. Credentials never leave the daemon.

## Why this exists

Downcroc already knew how to ingest replies, thread mail, and send through the
right transport. What it lacked was a way for someone else to add a behavior on
top of that machinery without editing the daemon. This release adds that seam.

The rule behind the design is simple: an extension never receives a password,
token, or vault path. It receives events and returns a list of capability calls.
The daemon checks grants, performs the action with credentials it already owns,
and returns a sanitized result.

## Architecture

All extension code lives in one vertical package, `src/downcroc/extensions/`.
Shared layers only gained wiring: the config schema, bootstrap, API app, CLI
parser, and dispatcher. The package holds:

- manifest and config parsing
- the capability broker and its handlers
- the process host and JSON line protocol
- the extension CLI and management API
- a small SQLite store for namespaced state and extension health

Manifests are TOML files in `~/.config/downcroc/extensions`. A manifest declares
an id, a run command, subscribed events, requested capabilities, and optional
commands it contributes to the CLI. User config enables it and grants a subset
of the requested capabilities.

## Trust modes

The default is subprocess. The daemon starts the extension as a child process
with a restricted environment, no vault variables, and no inherited file
descriptors beyond standard input and output. It speaks newline-delimited JSON:
a `hello` message on start, an `event` for each subscription, and a `result`
after the actions run. This works with Python or any other language.

An extension written by the user can set `trust = true` to run in-process. That
uses the same broker but is not sandboxed. The config field makes the choice
visible, and `extension.started` records the mode in the log.

## Capability model

Every capability is default deny. The manifest declares what the extension
wants; config grants what it may use. Wildcards such as `mail.*` are accepted
for convenience, but each call is logged with the concrete capability.

The broker counts real SMTP sends for `smtp_seat_max_sends`, rate limits calls
and send actions per extension, and redacts credentials from logs, events, API
responses, errors, and backups. A capability cannot return a raw secret.

`http.request` is the general escape hatch for custom credentialed work. It
accepts a credential reference, injects authentication in the daemon, enforces
a per-extension host allowlist, and returns a sanitized response. The extension
never sees the token.

The system and integration families include a few registered names that are not
yet backed by a full daemon operation. They return a structured acknowledgement
and are logged like any other call. Do not rely on their side effects in this
release. The mail reply path, inspection, KV, and logging are fully wired.

## Safety

- Extension sends carry the extension id and do not re-trigger the hook that
  caused them.
- Chained extension events are depth limited.
- Crashes and timeouts are logged and restarted up to `extensions.max_restarts`.
- Every call writes `extension.call`, `extension.denied`, or
  `extension.call_failed` with the extension id, capability, outcome, and
  duration.
- No filesystem, environment, shell, or direct database capability is exposed.

## CLI and API

The new `downcroc extension` command covers `list`, `show`, `add`, `enable`,
`disable`, `reload`, `logs`, `capabilities`, `test`, and `run`. Commands declared
by a manifest also appear as normal downcroc commands and route back through
the daemon.

An additive loopback API under `/api/extensions` backs the CLI. It uses the
existing bearer auth and Host and Origin validation. No API version changed.

## Storage and upgrade

A generated Alembic revision adds `extension_kv` for namespaced extension state
and `extension_state` for health and enablement. The daemon runs it at startup
like every other migration. No configuration change is required, and the
extension host starts disabled for manifests until an extension is enabled
explicitly.

## What you should see

Write a manifest, add it with `downcroc extension add`, reload, then enable the
extension. When someone replies to a campaign mail, an extension subscribed to
`reply.attributed` can call `mail.reply` with the inbound message id and a text
body. The daemon sends the reply in the same thread using the original account,
and the log records the extension id on the send event.

Read-only commands such as `batch list`, `account show`, and capacity views do
not start or rotate extensions. The SMTP seat rules from earlier releases still
apply to all sends, including extension sends.

## Acceptance

Black-box tests start a real daemon, install a fake extension, and verify:

- a confirmed reply produces exactly one threaded `mail.reply`
- the extension process sees no vault environment or raw credential
- an ungranted capability is denied and logged
- KV state and extension health survive restart
- the CLI lists, enables, disables, tests, and runs extension commands

The docs map, glossary, lock check, compileall, ruff, and format checks all pass.
