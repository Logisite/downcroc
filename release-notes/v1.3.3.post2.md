# 1.3.3.post2

Follow-up messages now thread reliably with the recipient, regardless of which send
transport was used for the parent or the follow-up.

## What changed

The Gmail API replaces the self-generated `Message-ID` header on delivery with its own
value. Follow-ups referenced the original self-generated id, so recipients saw each
follow-up as a new top-level message instead of a reply in the same conversation. SMTP
does not rewrite the header, which is why threading only broke on the API path.

The daemon now records the Message-ID that was actually delivered:

- New sends store the delivered id at send time (read back from Gmail for API sends,
  the minted id for SMTP sends).
- Older API sends recover the delivered id in the background or on demand when a
  follow-up needs it, using the provider id already stored on the send attempt.
- SMTP jobs from older databases are backfilled by the migration with pure SQL.

Follow-ups then build their `In-Reply-To` and `References` headers from the parent's
delivered id. The self-generated id remains the fallback for mail that can no longer be
recovered, so behavior never regresses. Every threading decision is logged, including
which id was used (`reference_source: delivered` or `minted_fallback`).

## What you should see

Follow-ups sent from a later campaign now appear inside the original conversation in
the recipient's inbox, whether the parent was sent over SMTP or the Gmail API. Existing
campaigns heal as their parent messages are recovered; all new mail is handled
correctly from the first send. No configuration change is required. The daemon runs the
new migration at startup, so restart the service after upgrading.
