# 1.3.5.post3

Fixes sticky SMTP seats being discarded by read-only commands and other
planning calls before the holder had sent anything.

## What changed

`SlotResolver.pick()` used to mutate the sticky holder on every call. Capacity,
ETA, batch listing, account show, and transport views all call it, often with a
single account filter. Those reads could release the holder with reason
`failover` or `idle`, and the next dispatch cycle logged a new seat with reason
`boot`. Auto-routed jobs made this especially visible because the extra capacity
and ETA calls came from more places.

Now only the dispatcher advances sticky state. Read-only views can inspect the
current plan without rotating it.

The old `idle` release is gone. A holder with no work in a cycle is not
discarded. Another working account may borrow the seat for that cycle, and the
holder keeps it for when its work returns. The holder is released only on a real
transport failure, a configured time cap, a configured send cap, or batch drain
when `smtp_seat_after_batch` is enabled.

`smtp_seat_max_sends` now counts successful SMTP sends, not planning calls.
`dispatch.smtp_seat` events now carry the real hold duration, real send count,
the previously held account, and a `source` field such as `dispatch` or
`query`. The `smtp_seat_after_batch` option is now wired up and documented.

## What you should see

With `dispatch.smtp_seat_sticky = true`, one mailbox keeps the SMTP seat through
normal dispatch cycles. Running `downcroc batch list`, `downcroc account show`,
or other read-only commands no longer produces `dispatch.smtp_seat` events with
zero sends. The seat changes only when a documented release condition fires.
No configuration change is required.
